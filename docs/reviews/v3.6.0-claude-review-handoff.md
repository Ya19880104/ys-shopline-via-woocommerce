## 1. Market and SHOPLINE review

The reviewed platform behavior supports an explicit intermediate payment-confirmation state. It does not support converting elapsed time alone into payment failure.

| Platform / evidence | Public behavior | Design consequence |
|---|---|---|
| [SHOPLINE order and payment statuses](https://support.shoplineapp.com/hc/zh-tw/articles/115005489043) | Order and payment state are separate operational concepts. | Do not represent an unsettled payment as paid, failed, or a fulfillment-ready order. |
| [SHOPLINE POS timeout handling](https://support.shoplineapp.com/hc/zh-tw/articles/24626094173209) | A timeout can still settle later; SHOPLINE asks merchants to wait up to three hours before treating it as unresolved. | Fifteen minutes can trigger a query, but can never be the failure verdict. |
| [SHOPLINE billing `付款處理中`](https://support.shoplineapp.com/hc/zh-tw/articles/57465143948057) | SHOPLINE itself uses a neutral processing state while a payment result is unsettled. | Customer copy should be neutral: `付款確認中`, not `授權成功` or `未扣款`. |
| [SHOPLINE create](https://docs.shoplinepayments.com/api/trade/create/), [query](https://docs.shoplinepayments.com/api/trade/query/), and [webhook](https://docs.shoplinepayments.com/guide/quick/) | Create response, later query, and asynchronous notification are separate convergence channels. | Query, redirect, hourly sync, and webhook must use one exact-attempt reconciliation contract. |
| [SHOPLINE LINE Pay expiry](https://support.shoplineapp.com/hc/zh-tw/articles/55865621726105) | Customer-action and expiry are distinct from a captured payment. | `CREATED` / `CUSTOMER_ACTION` stay in the prior-trade resolver; exact expiry may reopen payment. |
| [Shopify authorization lifecycle](https://help.shopify.com/zh-TW/manual/payments/payment-authorization/) | Authorized and captured are distinct. | `AUTHORIZED` must not be treated as paid or fulfillment-ready. |
| [CYBERBIZ repayment](https://help.cyberbiz.io/ec/orders/order-settings/provide-payment-link/) and [EasyStore unpaid/auto-cancel](https://support.easystore.co/zh-tw/article/44cq5yqf6io96kit5a6a44cr6zec5pa857wq5biz6kit5a6a-puvdde/) | Repayment is available after an order is authoritatively unpaid/cancelled, not while settlement is unknown. | Keep repayment locked until an exact terminal result is known. |
| [ECPay transaction status documentation](https://developers.ecpay.com.tw/wp-content/uploads/2023/09/%E7%B6%A0%E7%95%8C%E7%AB%99%E5%85%A7%E4%BB%982.0%E6%96%B0%E5%9E%8B%E9%96%98%E9%81%93%E6%8A%80%E8%A1%93%E6%96%87%E4%BB%B6-App.pdf) and the supplied PAYUNi `UNKNOWN` evidence | Taiwan gateways can return an indeterminate result and deliver/query the final result later. | Unknown must be fail-closed and queryable; it is not a safe retry signal. |

### Plan corrections applied

1. One WooCommerce status is used: `wc-ys-confirming`, label `付款確認中`.
2. Internal reasons remain separate: `authorized`, `in_flight`, `indeterminate`, `bnpl_review`.
3. Card/wallet query stages are cumulative at approximately 2m, 5m, 15m, 30m, 1h, 3h, and 6h.
4. BNPL query stages are cumulative at approximately 5m, 15m, 1h, 6h, and 24h.
5. Elapsed time is never terminal. Final unresolved stage stays locked and becomes a manual-review item.
6. Only an exact paid result completes payment; only exact FAILED/EXPIRED/CANCELLED reopens payment.
7. `CREATED` and `CUSTOMER_ACTION` return to the existing prior-trade resolver instead of being declared failed.
8. ATM virtual-account pending flow and subscription recurring fail-closed flow remain separate.

## 2. Production implementation

### New ownership boundary

- `src/Utils/YSConfirmationPolicy.php`
  - Pure status families, neutral reasons, query schedules, and the contract that elapsed time is never terminal.
- `src/Handlers/YSPaymentConfirmation.php`
  - Custom status registration, exact attempt metadata, scheduler, strict query/webhook convergence, MySQL named lock, terminal notification, paid-history repair, and manual-review escalation.

### Integrated paths

- `YSGatewayBase`: blocks a new reference before create when an active confirmation exists; records the exact non-sensitive request envelope; enters confirmation for accepted in-flight or unknown results.
- `YSRedirectHandler`: routes query errors/in-flight/unknown into the same lifecycle and preserves immediate terminal failure behavior.
- `YSStatusManager`: delegates confirming orders to the exact reconciler; hourly sync remains a safety net.
- `YSWebhookHandler`: exact paid/terminal convergence, in-flight entry, and paid-history guards for late AUTHORIZED/PROCESSING/CUSTOMER_ACTION/FAILED/CANCELLED/EXPIRED events.
- Main plugin order-pay AJAX: checks authorization first, blocks active confirmation before `needs_payment()`, and reloads the order after gateway processing to avoid stale state.
- `YSCreditSubscription`: excludes all new attempt/confirmation meta from renewal-order copying. Recurring charge routing was not changed.
- Admin: confirmation review appears in the existing SLP review column/banner without overwriting abandoned-payment review data.
- Frontend: neutral confirming and terminal copy on thank-you/My Account; terminal copy now also appears on the standard `order-pay` form without adding a duplicate payment button.

## 3. Independent findings fixed during implementation

1. WCS renewal initially inherited new confirmation meta. All new meta is now excluded.
2. Final confirmation review was initially invisible in the existing SLP queue. Admin visibility was added without sharing the abandoned-payment flag.
3. Late non-paid webhook families could still mutate an order with paid history. All six event families now no-op with an audit note.
4. `CUSTOMER_ACTION` discovered after an unknown result was initially kept locked. It now returns to pending with trade ID preserved for `resolve_prior_trade()`.
5. Query/webhook convergence was not serialized. Order-scoped MySQL `GET_LOCK` now wraps exact convergence and always releases in `finally`.
6. A paid-history order stuck in confirming could remain there or replay `payment_complete()`. It now restores paid status without replaying payment hooks.
7. Async terminal handling initially notified only the customer. Customer and merchant notifications are now independently recorded per reference.
8. Transition detail was initially hidden only in meta. Idempotent structured order notes now expose reason/status/reference/trade/stage/source.
9. Hourly sync could bypass strict session-only reconciliation. It now delegates to the lifecycle service.
10. Browser testing found the terminal notice missing from `order-pay`. A standard WooCommerce `woocommerce_pay_order_before_payment` hook and executable contract were added.
11. Claude round 1 found three stale v3.5.38 JS comments. They now describe the v3.5.39 card/installment capability model without changing executable frontend behavior.
12. Claude's 37-item scratch regression scan was not reproducible. A 43-sentinel `tests/regression-scan.php` is now versioned, executable standalone, and included in `php tests/run.php`.
13. The final observation stage originally had only an admin column marker, order note, and log. It now sends one high-priority store-admin email per `manual_review:{reference}` key; it never emails the customer without a terminal result and cannot suppress the later terminal customer/admin notification.
14. A customer LINE Pay video exposed an unversioned test gap: the exact `WP_Error(http_request_failed)` create path had not been executed by the repository contract suite. The production path was already correct in v3.6.0, but the bootstrap had never loaded `YSRedirectHandler` for this branch. The versioned gateway contract now proves one create call, a durable `ys-confirming` transition, thank-you redirect, cart clear, and zero create calls on an immediate retry while preserving the exact reference.

### Claude round-1 disposition

- **F4 / legacy migration:** intentional event-driven migration retained. A stale legacy flag is not enough evidence for a bulk lock; synchronization/webhook events migrate exact attempts safely.
- **F6 / manual cancellation:** review marker intentionally remains. A WooCommerce status change is not proof of the SHOPLINE result; removing the warning would hide unresolved payment risk.
- **F7 / BNPL 24h:** retained as escalation-only. It stops polling and enters review but never marks failure or unlocks payment; real merchant duration data should drive any later configurability.
