# v3.6.1 Claude Review Handoff

Date: 2026-07-19

## Verdict requested

Please review the v3.6.1 code as a wallet confirmation-lock harm-reduction release. The customer incident proves that an indeterminate lock existed, but the original response that created that lock is not available. This change therefore does not claim to have identified or removed the initial upstream cause.

## Confirmed defect fixed

When a LINE Pay or Apple Pay create request was classified as unknown before a trade ID was persisted, a later exact `trade.customer_action` webhook could not find the order by trade ID. The order stayed locked until the scheduled confirmation lifecycle or a terminal webhook converged it.

v3.6.1 now:

1. Falls back to the plugin reference only for an order that is still in the confirmation lifecycle.
2. Requires the active attempt to match reference, trade ID, SHOPLINE payment method, amount, and currency.
3. Adopts the trade ID, clears the confirmation and indeterminate locks, and returns the order to `pending` for the existing prior-trade resolver.
4. Keeps the trade ID so switching to ATM still performs query, cancel, and re-query. A query failure remains fail-closed and cannot create a second trade.
5. Never lets a delayed webhook for attempt `X_1` unlock active attempt `X_2`.

## Unknown diagnostics

Create-trade unknown paths now log a safe structural envelope:

- HTTP status and SHOPLINE request ID
- exact error code and message
- top-level response key names
- whether `tradeOrderId` and `nextAction` were present
- payment error code/message when supplied
- WordPress transport error when no HTTP response was received

Raw response bodies, pay sessions, customer tokens, and credential values are not retained. `YSApiException` transports this context into `WP_Error` data, and `YSApiError::diagnostic_context()` provides one normalized logging boundary.

## Scope boundaries

- No ATM business logic changed.
- No checkout JavaScript changed.
- No subscription or recurring-payment decision changed.
- The shared API change only propagates diagnostics; rejected/unknown classification and fail-closed behavior are unchanged.
- Apple Pay cannot be faithfully created by a pure server `{}` pay-session simulation because the SDK supplies `referenceMerchant.StoreWebsite`. Real Apple Pay cancellation still requires an eligible Apple device/browser.
- A successful customer-action unlock does not promise immediate repayment: if the retained prior trade cannot be queried, the resolver correctly keeps the order blocked and asks the customer to retry later.
