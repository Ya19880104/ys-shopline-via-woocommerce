# v3.6.2 Return Confirmation and Customer Recovery

## Problem

1. A wallet payment can return to WooCommerce before SHOPLINE's query endpoint reports the final paid state. When the first query returns `CREATED` or `CUSTOMER_ACTION`, v3.6.1 leaves the order in ordinary `pending`, so the thank-you page incorrectly offers payment again until the paid webhook arrives.
2. The shared `Regular` request fallback adds `paymentCustomerId` to every gateway whenever the user has local credit-card tokens. This leaks stale credit-customer identity into LINE Pay and other ordinary payment requests and can produce SHOPLINE error `1005 Enable Customer not found` after a site/environment migration.

## Decisions

- On a valid SHOPLINE return URL, non-ATM customer-pending states enter `wc-ys-confirming`. This is a display and payment-lock correction for an already-created exact trade, not a change to the initial `nextAction` flow.
- Keep the existing first card/wallet reconciliation at 120 seconds. A paid LINE Pay result has been observed to become visible roughly one minute after return; shortening the first stage to 30 seconds would expose repayment while the original wallet attempt can still settle.
- Do not provide a direct "change payment method" bypass, including ATM. The confirmation lock belongs to the unresolved original attempt, not the replacement method. An issued ATM account can still be paid later after the old wallet succeeds, so ATM is not a no-double-payment exception. Exact paid, terminal, or customer-action convergence must run first.
- Treat paid history as monotonic. Webhook, redirect, manual/hourly query, immediate create response, and subscription renewal share one order-scoped payment-completion lock; a late non-paid query cannot move a paid order backward or replace its paid metadata.
- SHOPLINE customer/card identity is permitted only for credit-card customer-bound flows. Wallet, ATM and BNPL must not query/create a card customer or carry `customerToken`/`paymentCustomerId`.
- Re-apply the capability boundary after frontend `sdkOptions` and backend `ys_shopline_payment_data` extension points, while preserving unrelated extension fields.
- Treat only error code `1005` whose structured/message text identifies `Customer not found` as a stale customer identity. Invalidate the exact matching user mapping and instruments cache; do not treat every `1005` as stale.
- If stale identity is detected while generating `customerToken`, recreate the customer once and retry token generation once. If detected after create-trade rejection, invalidate for the next page load and keep the response rejected/retryable; never retry the trade automatically.
- Do not automatically delete WooCommerce payment tokens or subscription payment metadata. They are audit evidence and may belong to live subscriptions; the rebuilt SHOPLINE customer will simply render no unavailable saved cards.

## Acceptance Criteria

1. LINE Pay/Apple Pay return query `CREATED` or `CUSTOMER_ACTION` changes an unpaid order to `ys-confirming`, stores the exact attempt and schedules reconciliation.
2. Paid, terminal, in-flight, unknown and ATM behavior remain unchanged.
3. LINE Pay and other non-credit flows neither query/create a card customer nor send `customerToken`/`paymentCustomerId`, even when local credit tokens exist.
4. Credit-card customer-bound `Regular` compatibility behavior remains unchanged.
5. Exact stale-customer `1005` conditionally removes only the matching customer meta plus instruments cache; unrelated `1005` and a concurrently replaced customer ID are untouched.
6. Token bootstrap repairs a stale customer once without recursion. Create-trade rejection never performs an automatic second trade create.
7. PHP contracts, Node contracts, regression scan, lint, package inspection and dev-checkout runtime/integration checks pass with no fixtures left behind.
8. Active wallet confirmation blocks replacement create calls for all eight gateways, including ATM, until exact convergence releases the attempt.
9. Query-first and webhook-first paid races execute WooCommerce payment-completion hooks once; late `PROCESSING` and other non-paid states cannot downgrade a paid/custom-paid order. Full refund remains an explicit allowed transition.
